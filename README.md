# マルチアカウント カレンダー相互同期

複数のGoogleアカウント（2つ以上、上限なし）のカレンダーを相互に同期する仕組み。Google Apps Script（GAS）で実装。

以下、例として3アカウント構成（「会社A」「個人」「会社B」）で説明する。

| # | アカウント例 | 用途例 |
|---|---|---|
| 1 | `account-a@example.com`（会社A・Workspace） | 本業 |
| 2 | `account-b@example.com`（個人・gmail.com） | 個人 |
| 3 | `account-c@example.com`（会社B・Workspace） | 副業 |

どのアカウントで予定を入れても、残りのアカウントのカレンダーにも自動で反映される（総当たり方式）。

## アーキテクチャ

各アカウントに1つずつ、**そのアカウント宛の**Apps Scriptプロジェクトを設置する（3アカウント構成なら計3プロジェクト）。各プロジェクトは「自分以外の全アカウント」を読み取り元（ソース）として、予定を2箇所にコピーする。

```
        読み取り(shareで許可)          読み取り(shareで許可)
  ┌───────────┐  ←───────────  ┌───────────┐  ←───────────  ┌───────────┐
  │  会社A     │                │  会社B     │                │  個人      │
  │  script   │  ───────────→  │  script   │  ───────────→  │  script   │
  └───────────┘   書き込み(自分)  └───────────┘   書き込み(自分)  └───────────┘
        ↑___________________________________________________________|
                          （残りの1辺も同様に双方向）
```

- Nアカウント構成なら、各アカウントのスクリプトが「自分以外の N-1 ソース」分をまとめて処理するので、デプロイするプロジェクトはNつで済む
- Workspace（業務）アカウント由来の予定は、勤務場所/不在イベント・タイトル「移動」「予定あり」・不参加(declined)の予定を除外
- 個人Gmailアカウント由来の予定はフィルタなしでそのまま転記

### 2層の書き込み（重要）

各ソース由来の予定は、**2箇所に別々の形で**書き込まれる。

| 層 | 書き込み先 | 内容 | 公開設定 | 目的 |
|---|---|---|---|---|
| **(1) 詳細層** | ソースごとの専用同期カレンダー（例「AccountA同期」、初回自動作成） | タイトル・説明・場所そのまま | **非公開(private)固定** | 本人が自分のカレンダーで予定の詳細を確認する |
| **(2) ブロック層** | **自分のプライマリカレンダー** | タイトル「予定あり」固定・説明はマーカーのみ・場所なし | **非公開にしない(default)** | 他メンバーが本人のプライマリを1つ見るだけで予定の埋まりを確認できる／ドメイン内のカレンダー検索でも「予定あり」として見える |

**なぜ2層か**: (1)だけだと、他メンバーが見るのは本人のプライマリなので、専用同期カレンダーに入れた予定は他メンバーに見えず、その時間が「空き」に見えてしまう（ダブルブッキングを防げない）。そこで(2)として、プライマリに直接「予定あり」ブロックを立てる。これにより **専用同期カレンダーを他メンバーに追加共有する必要がない**（既存のプライマリ共有だけで完結する）。

### 除外条件（Workspace系アカウント由来の予定のみ）

- `eventType` が `workingLocation`（勤務場所）または `outOfOffice`（不在）
- タイトルが `EXCLUDED_TITLES`（既定: 「移動」「予定あり」）に**完全一致**する予定
- 自分（各アカウントの `selfEmail`）が **不参加（declined）** にしている予定

### 共通仕様

- **頻度**: 各15分おき（時間トリガ）
- **対象期間**: 現在時刻 〜 未来60日（過去は同期しない）
- **レート制限対策**: 1実行あたり最大30件、操作間に200msスリープ。超過分は次回トリガに繰り越し。詳細層＋ブロック層で1予定あたり最大2書き込みするため、初回同期は数回のトリガに分かれる
- **時系列ソート**: 直近の予定から処理されるよう時系列ソートしてから処理

## 前提条件

- 各アカウントの**プライマリカレンダーのデフォルト公開設定が「非公開」になっていない**こと（通常の初期設定=共有権限に従う、でよい）。ブロック層の予定はプライマリのデフォルト設定を継承するため、ここが「非公開」だと他メンバー/他アカウントから中身が見えず、後述のループ防止マーカーも読めなくなる
- Google Workspace アカウントを使う場合、ドメイン内のカレンダー相互参照が管理者設定で有効なこと

## クイックスタート（Claude Code 推奨）

このリポジトリを clone して Claude Code で開き、「カレンダー同期をセットアップして」と伝えれば、`CLAUDE.md` の指示に従って対話的に各自の `Code.gs` を生成してくれる。同期したいアカウント数・メールアドレス・Workspaceか個人Gmailかを聞かれるので答えるだけでよい。

## 手動セットアップ手順

### A. カレンダー共有

全アカウントそれぞれで、**自分のプライマリカレンダー**（および同期したい追加カレンダー）を残り全アカウントに共有する。手順はどのアカウントでも同じ:

1. https://calendar.google.com を該当アカウントで開く
2. 共有したいカレンダーの「︙」→「設定と共有」
3. 「特定のユーザーまたはグループと共有する」→ 共有先のメールアドレスを追加
4. 権限: **「予定の表示（すべての予定の詳細）」**

3アカウント構成の場合、必要な共有の組み合わせ（6件）:

| 共有元 | 共有先 |
|---|---|
| 会社A プライマリ | 個人, 会社B |
| 個人 プライマリ | 会社A, 会社B |
| 会社B プライマリ | 会社A, 個人 |

> ⚠️ Workspace アカウントの場合、管理者設定で外部共有がブロックされていると「すべての予定の詳細」で共有できない場合がある（権限選択肢がグレーアウトする）。IT管理者に「外部ドメインと予定の詳細を共有できるようにする」設定を依頼する。

> 補足: ブロック層は自分のプライマリに書き、詳細層は自分のアカウント内の専用カレンダーに書くだけなので、上記以外に追加の共有設定は不要。特に専用同期カレンダー（「AccountA同期」等）を他メンバーに共有する必要はない。

### B. 各アカウントへのGAS設置

全アカウントとも手順は同じ。それぞれのアカウントで作業する。

1. https://script.google.com を該当アカウントで開く
2. 「新しいプロジェクト」→ 名前をわかりやすく変更（例:「calendar-sync-会社A」）
3. デフォルトの `Code.gs` を `template/Code.gs` の内容で全置換
4. `SOURCES` 配列を、「自分以外の全アカウント」で埋める（各プロパティの意味は `template/Code.gs` 内のコメント参照）
5. `appsscript.json` の内容も `template/appsscript.json` で置き換える（マニフェストファイルの表示は Apps Script エディタの「プロジェクトの設定」→「"appsscript.json" マニフェスト ファイルをエディタで表示する」を有効化すると出てくる）
6. 保存
7. `syncCalendar` を実行 → 権限承認。初回実行時に該当する専用カレンダーが自動作成される
8. ログに `[<ソース名>] loaded N events from ...` がソース分すべて出ているか、`[<ソース名>/secondary]` `[<ソース名>/primary]` の処理件数ログが出ているか確認
9. `installTrigger` を実行 → 15分おきトリガが設定される

## 動作確認

- いずれかのアカウントに新規予定を追加 → 15分以内に:
  - 残りのアカウントの**専用カレンダー**に、転記元固定の色でタイトル・説明・場所そのままの予定（非公開）が現れる
  - 残りのアカウントの**プライマリ**に、タイトル「予定あり」のブロック（非公開でない）が現れる
- 元の予定を削除すると、両方の転記先から消える
- 他メンバーが対象アカウントのプライマリをカレンダー検索で開くと、「予定あり」ブロックでその時間が埋まって見える
- 不参加にした会議招待（Workspace系由来）、タイトルが「移動」「予定あり」の予定は転記されない

すぐ確認したい場合は各スクリプトの `syncCalendar` を手動実行。

## ループ防止の仕組み

**構造的分離 ＋ 普遍マーカー除外の二重防御**でループ（自分が転記した予定を他アカウントが再度転記してしまうエコー）を防いでいる。

### 1. 普遍マーカー除外（主防御）

本システムが書き込む予定の description には必ず同期マーカー `[calsync:` が入る（詳細層・ブロック層とも）。各スクリプトはソース予定を読み込んだ直後、**description に `[calsync:` を含む予定を最優先で除外**する（ワークスペース系フィルタより前段、Advanced API・CalendarApp 両方の読み込み経路に無条件適用）。

これにより、あるアカウントのプライマリに立てた「予定あり」ブロックを他アカウントが読み込んでも、マーカーで弾かれて再転記されない。多段連鎖も、2段目の読み込み時点でマーカー除外され停止する。

### 2. ブロック層をあえて「非公開にしない」理由

上記マーカー除外が機能する前提は「**他アカウントがブロック層予定の description を読めること**」。Googleカレンダーの仕様上、**予定単位で「非公開(private)」に設定すると、共有権限が「すべての予定の詳細」でも、共有先からは色・説明を含めて『予定あり』としか見えなくなる**。そのため、ブロック層を非公開にするとマーカーが読めず、除外できず、無限エコーが再発する（実運用で確認済みのバグパターン）。

よってブロック層は **visibility=DEFAULT（非公開にしない）** で書く。これにより他アカウントはマーカーを読めて除外でき、かつ他メンバーからは「予定あり」ブロックとして見える（一石二鳥）。

### 3. 詳細層の構造的分離（副防御）

詳細層（専用同期カレンダー）は非公開かつ、**どのアカウントのソースリストにも含まれない**ので、そもそも誰にも読み込まれない。仮にマーカー除外が何らかの理由で漏れても、詳細層由来のエコーは構造的に発生しない。

### source_id による重複・更新管理

上記とは別に、各層は自分の書き込み先での「既存の同期予定を更新するか／新規作成するか／削除するか」の判定に description 内の `source_id:xxxx` タグを使う。詳細層とブロック層は別カレンダー・別タグ（`-v<N>` と `-primary-v<N>`）なので、`source_id` が同値でも混ざらない。

## 運用上の重要な注意

過去の実運用で判明した、特に注意すべき4点:

1. **複数アカウントのスクリプトは同じタイミングで導入・更新する**。マーカー除外のない旧版が混在すると、旧版アカウントが新版アカウントのブロック層をマーカー無しで再転記してしまい、エコーが起きる
2. **Workspace アカウントは「すべての予定の詳細」共有が確認できるまでソースに加えない**。時間枠のみの共有（フリー/ビジー）だとマーカーを含む description が読めず、エコーのリスクがある
3. **移行・やり直し時は `purgeAllHistory` を各アカウントで実行してから回す**。中途半端な状態で `syncCalendar` を回すと、旧タグ・新タグの予定が混在して収束が遅れる
4. **終日予定のブロックはGoogleの仕様で空き時間扱いになる**（画面上は見えるが、空き時間検索では「空き」として扱われる）。ダブルブッキング防止の完全な保証にはならない

## リセット方法

| 関数 | 対象カレンダー | 期間 | 件数上限 | 用途 |
|---|---|---|---|---|
| `purgeSyncedEvents` | 各ソースの専用カレンダー＋プライマリ | 前後365日 | 30件/回 | 通常運用中の軽いクリーンアップ |
| `purgeAllHistory` | **プライマリ＋各専用カレンダーの両方** | **前後3年** | **なし（一括）** | `purgeSyncedEvents`で消しきれない時の緊急一括削除 |

いずれも `SOURCES` に登録された全ソース分（詳細層タグ・ブロック層タグ・旧タグすべて）を一括処理する。自分のタグ（`[calsync:...]`）が付いた予定だけ消えるので、手で作った予定は無事。

## カスタマイズポイント

各 `Code.gs` 先頭の `SOURCES` 配列の要素（ソースごとの設定オブジェクト）を編集する。

| プロパティ | 説明 |
|---|---|
| `key` | ログ・同期タグ・カレンダー名に使う識別子 |
| `calendarIds` | 読み取り元カレンダーIDの配列。プライマリはメールアドレスそのもの |
| `filterWorkspaceStyle` | `true`=業務アカウント向けフィルタ適用（eventType/declined/除外タイトル）、`false`=フィルタなしでそのまま転記 |
| `selfEmail` | `filterWorkspaceStyle: true` の場合、declined判定に使う自分のメールアドレス |
| `targetCalendarName` | 詳細層の書き込み先の専用カレンダー名。存在しなければ自動作成 |
| `color` | 転記した予定に付ける色（`CalendarApp.EventColor`） |
| `tagVersion` | 詳細層タグのバージョン番号 |
| `legacyTags` | 自動削除対象にする旧バージョンの詳細層タグ一覧 |
| `broadcastBusyOnPrimary` | `true`=プライマリに「予定あり」ブロック（ブロック層）を出す |
| `placeholderTagVersion` | ブロック層タグのバージョン番号 |
| `legacyPlaceholderTags` | 自動削除対象にする旧バージョンのブロック層タグ一覧 |

その他の全ソース共通設定:

| 定数 | 説明 |
|---|---|
| `EXCLUDED_TITLES` | 転記しないタイトルの完全一致セット（既定: 「移動」「予定あり」） |
| `ALLOWED_EVENT_TYPES` | 転記する eventType 集合（既定: default + focusTime） |
| `PLACEHOLDER_TITLE` | ブロック層の固定タイトル（既定: 「予定あり」） |
| `GLOBAL_SYNC_MARKER` | 普遍エコー除外マーカー（既定: `[calsync:`）。**変更する場合は全タグのプレフィックスと揃えること** |
| `PAST_DAYS` | 過去何日まで同期対象にするか（既定: 0） |
| `FUTURE_DAYS` | 未来何日まで同期対象にするか（既定: 60） |
| `MAX_OPERATIONS_PER_RUN` | 1実行あたりの最大処理件数（既定: 30） |
| `SLEEP_MS_BETWEEN_OPS` | 各操作の間隔ミリ秒（既定: 200） |

### アカウントを追加する場合

1. 新アカウントのプライマリ（＋必要なら追加カレンダー）を既存の全アカウントに共有する
2. 既存アカウント全ての `Code.gs` の `SOURCES` に新アカウントのソース設定を1件追加する
3. 新アカウント用の `Code.gs`（既存いずれかのファイルをコピーしてOK）を作り、`SOURCES` に既存アカウント分を設定する
4. 追加後の全アカウント分で `syncCalendar` → `installTrigger` を実行する

## トラブルシュート

### 他メンバーからプライマリの「予定あり」ブロックが見えない

- 本人のプライマリのデフォルト公開設定が「非公開」になっていないか確認（共有権限準拠=default であること）
- Google Workspace のドメイン内カレンダー共有ポリシーが有効か（管理者設定）
- どうしても読めない場合の最終手段として、ブロック層の visibility を `DEFAULT` から `PUBLIC` に変える手もあるが、ドメイン外への露出が増えるので通常は不要

### 予定が重複転記される／エコーが止まらない

まず考えられるのは、ブロック層が誤って非公開になっているケース。`writeEvent` でブロック層(MODE_PLACEHOLDER)の `visibility` が `DEFAULT` になっているか、`GLOBAL_SYNC_MARKER` 除外フィルタが両方の読み込み経路（`loadViaAdvancedApi` / `loadViaCalendarApp`）に効いているかを確認。`purgeAllHistory` で一旦全消ししてから `syncCalendar` を回し直すのが早い。

### `Exception: You have been creating or deleting too many calendars or calendar events in a short time.`

Google カレンダー API のレート制限。詳細層＋ブロック層で書き込みが増えたため初回は当たりやすい。

スクリプト側で 1実行30件まで に制限してあるので、初回は何回かトリガを待てば残りを順次処理してくれる。エラー直後はGoogle側でレート制限カウンタが残っているため、1〜2時間ほど待ってから再度手動実行するか、15分おきトリガに任せる。

それでも繰り返しレート制限に当たる場合：
- `MAX_OPERATIONS_PER_RUN` を 10〜15 に下げる
- `SLEEP_MS_BETWEEN_OPS` を 500〜1000 に上げる
- `FUTURE_DAYS` を 14〜30 に減らす

### プライマリが「予定あり」ブロックで埋まって見づらい

仕様（他メンバーに見せるため意図的にプライマリへ出している）。本人の詳細確認は専用同期カレンダー（詳細層）側で行う想定。将来的に期間を短くしたい場合は、ブロック層だけ別の未来日数にする拡張余地がある（現状は `FUTURE_DAYS` を詳細層と共用）。

### 特定のカレンダーの予定が転記されない

1. **共有未設定**: 上記「A. カレンダー共有」が未実施。共有先アカウントに「すべての予定の詳細」権限で共有されているか確認
2. **`calendarIds` への追加忘れ**: 該当する `Code.gs` の `SOURCES` 内、対象ソースの `calendarIds` に該当カレンダーIDが入っているか確認
3. **順番待ち**: 対象予定数が多いとレート制限の繰り越しで処理が遅れる。`loaded N events from <ID>` がログに出ていれば読み込みは成功しているので、数回のトリガを待つ
4. **不参加の予定・除外タイトル**: 自分が declined にした予定、タイトルが「移動」「予定あり」の予定は仕様により転記されない（`filterWorkspaceStyle: true` のソースのみ）

### `Calendar Advanced Service にアクセスできません`

B手順で `appsscript.json` を反映し忘れている（`filterWorkspaceStyle: true` のソースを含むプロジェクトは全て必要）。エディタの「サービス」セクションに `Calendar` が表示されているか確認。

### カレンダーIDにアクセスできません

カレンダー共有設定が反映されていないか、カレンダーIDのスペルミス。共有直後は数分かかる場合もある。

### Apps Script が「管理者により制限されています」と表示される

該当アカウントのWorkspace管理者設定で個人スクリプトの利用が制限されている可能性。IT管理者に許可申請が必要。

### 専用カレンダーが二重に作られてしまった

`getOrCreateCalendar` は名前一致で検索するため、手動で同名カレンダーを作った場合など複数存在すると意図しない方を使う可能性がある。カレンダー一覧設定でどちらが空かを確認し、不要な方を削除するか名前を変えて `targetCalendarName` を書き換える。
